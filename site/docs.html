Install

shell
npm install anchor-ai-sdk

Node 22+, ESM. The package root carries the whole engine; backends live behind subpaths — anchor-ai-sdk/sandbox/docker, /sandbox/heyo, /sandbox/local — and the conformance kit is at anchor-ai-sdk/testing. While the SDK is 0.x, pin exact versions.

Quickstart

A working agent is an llm, an agent, and a task. llmFromCatalog reads the model's real prices and context window from the provider catalog, so budgets and compaction configure themselves correctly.

chat.mjs
import { chatAgent, llmFromCatalog, runAgent } from "anchor-ai-sdk";

const { llm } = await llmFromCatalog({
  baseUrl: "https://openrouter.ai/api/v1",
  apiKey: process.env.OPENROUTER_KEY,
  model: "z-ai/glm-5.3",
});

const result = await runAgent(
  { task: "Explain what this repository does" },
  { llm, agent: chatAgent },
);
console.log(result.summary);

runAgent resolves with an AgentResult — the summary, the evidence trail (result.evidence), the last checkpoint ref, and the run's usage. Reasoning is streamed but journaled; it is never re-sent to the model.

Give it a machine

A sandbox is created from a repo + ref, handed to the run, and destroyed when you're done. Swap docker() for heyo() to run the same code on Firecracker microVMs.

repo-triage.mjs
import { codingAgent, runAgent } from "anchor-ai-sdk";
import { docker } from "anchor-ai-sdk/sandbox/docker";

const sandbox = docker().create({
  repoUrl: "https://github.com/you/your-repo",
  ref: "main",
});
await sandbox.start();
try {
  const result = await runAgent(
    { task: "Run the tests and fix the failing case" },
    { llm, agent: codingAgent, sandbox },
  );
  console.log(result.summary, result.checkpointRef);
} finally {
  await sandbox.destroy();
}

More runnable examples live in the repo's examples/ — including a non-coding agent with its own strategy and tool, no sandbox.

Engine & budgets

Budgets bound the loop in steps, tokens, and dollars (BudgetLimits). The engine tracks usage against the live prices from the catalog and hands out the numbers your app needs:

budgets.ts
const result = await runAgent(
  { task: "Fix the failing test" },
  {
    llm,
    agent: codingAgent,
    sandbox,
    budgets: { maxSteps: 60, maxUsd: 3 },
  },
);

Guardrails are on by default, each with an off switch — repeated-call detection, silent-tool advisories, and a materialization nudge when the agent goes long stretches of tools with nothing visible to say. Heartbeats and cross-process cancel polling are owned by the engine, so a run is never orphaned.

Phases (understand → plan → act → validate → respond) describe the approach for the model and your UI. They are never a second gated execution engine: pauses happen at phase boundaries when you ask for them, and nothing interleaves with the loop's single call path.

Memory & notes

The thread is the source of truth. A ThreadStore persists { summary, messages, phase } across runs — MemoryThreadStore ships for development; an app provides the durable one. Compaction is derived from the model's real context window, not a guess, and reasoning is journaled but never re-sent.

Notes ride your checkpoints. Agents keep working notes at the reserved .anchor/notes.md: it's git-excluded from status and diffs, and force-added into every checkpoint commit — so durability carries the agent's own memory alongside the repo, and notes never appear in the diff you ship.

Oversized output spills instead of vanishing. Every tool result is truncated and routed through one boundary: over the limits (300 lines / 20k chars by default; 60% head, 40% tail kept), the full output is written to the sandbox at <scratch>/out/ and the model gets a pointer — read slices with read_file(path, offset, limit), or search it with search(path, pattern). Nothing untruncated ever reaches the context; nothing readable is ever lost.

Revival & snapshots

A run that dies — out of budget, out of time, out of luck — leaves a handoff via the request_revival tool. planRevival and ThreadBudget decide how to fund the next run so it continues the same task, phase, and budget. When the thread's caps are spent, a human gets the note — quoting the agent's own words on what remains.

Snapshots are a persistence concern. The default hook is git-backed: at turn boundaries it commits the tree — only when something actually changed vs HEAD (no empty commits) — with the notes file force-added. Push is optional; supply a branch and the checkpoint leaves the machine. hasChangesFrom compares trees, so checkpoint-only changes are never mistaken for new work.

Streaming & traces

One wire path: every model call streams. Text and reasoning deltas, tool calls, compaction, checkpoints, and finishes all arrive as typed events — run_started, phase_started, llm_call_started, llm_reasoning_delta, llm_text_delta, llm_call_finished, tool_call, tool_result, advisory, checkpoint.

One fanout, one sequence number. A TraceFanout assigns the order once and redacts before every sink — an NDJSON file (JsonlTrace), your database rows, a live projector — so recording and replay can't drift. Redaction runs at the persistence boundary; tokens, keys, and user:pass URLs never reach disk.

The contract

One SandboxProvider interface, one Sandbox data model: create from repo + ref, exec with real kill deadlines, checkpoint with an optional push, hasChangesFrom for tree comparisons, a scratch directory outside the repo (spills and notes), git identity handling, and fork where the backend declares it. Tools never bypass exec — the tool-call contract is enforced once, in the adapters.

Store-backed sessions give continuity for free: a session can be retained, adopted by a later run, and fallen back to a rebuild when the machine is gone. Capabilities are promises — not suggestions.

Conformance

A backend is "done" when the executable conformance suite passes: exec fidelity, kill deadlines, env secrets, checkpoints, retain/adopt, git identity, pushes, and forks where declared.

conformance.ts
import { runSandboxConformance } from "anchor-ai-sdk/testing";

await runSandboxConformance(myProvider);

Tools & strategies

Tools are what the model sees. defineTool takes a JSON-Schema definition and an implementation; thrown validation errors become ok: false results instead of crashing the run. content is what goes back to the model — already truncated at the boundary — while meta stays on the trace.

tool.ts
import { defineTool, requireString } from "anchor-ai-sdk";

const lookupUser = defineTool(
  {
    name: "lookup_user",
    description: "Fetch one user by id",
    parameters: {
      type: "object",
      properties: { id: { type: "string" } },
      required: ["id"],
    },
  },
  async (input) => ({
    ok: true,
    content: await fetchUser(requireString(input, "id")),
    verb: "Looking up a user",
  }),
);

The built-in bundles pair a strategy with its toolset: chatAgent (no sandbox) and codingAgent (shell, file I/O, search, run_tests, and the finish tool). Custom strategies implement the same Strategy interface — phases you declare, tools you pick.

Testing

The package tests itself like it asks you to test it: the engine, tools, and trace layer run against fakes and fixtures with no network, every provider scenario runs in CI (local conformance always, Docker conformance on a purpose-built image, live microVMs opt-in with your own credentials), and executable genericity guards keep the package consumer-neutral — no product nouns, no environment reads.
